# 02. Engineering Standards

These rules apply to every line of code, whoever writes it. They exist so the app is still healthy at 99% complete.

## 1. Code style

- TypeScript `strict: true`, plus `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride`.
- No `any`. If a type is truly unknown, use `unknown` and narrow it. `// @ts-expect-error` needs a comment explaining why and a linked task to remove it.
- ESLint (shared config in `packages/config`) and Prettier. CI fails on any lint error. Warnings are not allowed to accumulate: zero warnings on `main`.
- File names: `kebab-case.ts`. React components: `PascalCase.tsx`. One component per file.
- Functions do one thing. If a function needs a comment to explain what each section does, split it.
- Prefer pure functions for business rules so they are easy to test. Put them in `packages/shared` when both client and server need them (for example price display, streak maths, time zone helpers).
- No magic numbers or strings. Named constants, enums from `packages/shared`.
- Comments explain **why**, not what.
- Dead code is deleted, not commented out.

## 2. Architecture rules (enforced)

| Rule | Enforcement |
|---|---|
| Modules import each other only via `index.ts` | ESLint `no-restricted-imports` + dependency-cruiser |
| No circular module dependencies | dependency-cruiser in CI |
| Clients never import server code | Package boundaries; `apps/*` cannot import `apps/api` |
| Vendor SDKs only inside `adapters/` (API) or a single wrapper file (clients) | ESLint `no-restricted-imports` per package |
| UI components contain no business logic or direct fetch calls | Review + lint rule banning `fetch` in components |
| AI SDK imported only in `modules/ai` and `adapters/llm` | ESLint |
| Database client imported only in repositories and `platform/db` | ESLint |

## 3. API design

- Contracts live in `packages/contracts/<module>/`. Each endpoint declares method, path, request schema, response schemas per status code, required permission and a summary.
- Paths: `/v1/<resource>`, plural nouns, kebab-case. Actions that are not CRUD use a sub-resource verb, for example `POST /v1/bookings/{id}/cancel`.
- JSON fields: `camelCase`. Dates as ISO 8601 strings in UTC. Money as `{ amountMinor: number, currency: "GBP" }`.
- Pagination: cursor-based (`?cursor=...&limit=...`), responses include `nextCursor`. Never offset pagination on growing tables.
- Every mutating endpoint that charges money, consumes credits, books a slot or creates a purchase accepts an `Idempotency-Key` header. The API stores keys for 24 hours and returns the original response on retry.
- **Compatibility:** after an endpoint ships to a store build, it can only change additively (new optional request fields, new response fields). Removing or renaming a field, tightening validation, or changing meaning needs a new version (`/v2/...`) and an ADR. `pnpm contracts:check` runs `oasdiff` against `main` and fails on breaking changes.
- **Minimum app version:** the API exposes `GET /v1/app-config` returning minimum supported and recommended app versions, feature flags for anonymous users, and purchase route configuration. The app checks it on launch and shows a blocking update screen if below minimum. We support every app version released in the last 6 months unless a security issue forces otherwise.

## 4. Database rules
Full detail in `03-data-model.md`. Summary:
- Migrations only, generated by drizzle-kit, reviewed by a human, committed with the code that uses them.
- Never edit a merged migration. Fix forward with a new migration.
- Expand and contract for any breaking change, spread over at least two releases.
- Every foreign key indexed. Every query used in a list endpoint has an index that supports it. `EXPLAIN` checked for new list queries.
- Long-running data backfills run as jobs in batches, never inside a migration.
- Migrations must be safe to run while the previous app version is live (no locking a big table for long, no dropping columns still read by old code).

## 5. Testing

### 5.1 What to test

| Layer | Tool | What | Required |
|---|---|---|---|
| Unit | Vitest | Pure business rules: pricing, credits maths, streaks, availability slot generation, permission maps, roadmap ranking | Every rule |
| Integration (API) | Vitest + Testcontainers Postgres | Each endpoint: happy path, validation failure, unauthenticated, forbidden, not found, idempotency where relevant | Every endpoint |
| Integration (jobs and events) | Vitest + Testcontainers | Each subscriber processes its event and is idempotent when run twice | Every subscriber |
| Webhooks | Vitest with recorded fixture payloads | Signature verification, idempotency, out-of-order delivery | Every webhook |
| Contract | `pnpm contracts:check` | No breaking change to shipped endpoints | Every PR |
| Web end to end | Playwright | Critical journeys: sign-up, checkout, coach portal booking management, admin moderation | Critical paths |
| Mobile end to end | Maestro | Critical journeys: onboarding, lesson playback, AI chat, booking, purchase (sandbox) | Critical paths |
| AI evaluation | Custom eval runner (`pnpm test:ai-evals`) | Voice, accuracy against Mia's content, ethics, safety, crisis routing, refusal handling | Every prompt or model change |
| Load | k6 | Key endpoints at 10x expected launch load | Before launch and each phase end |
| Accessibility | axe (web), manual VoiceOver and TalkBack passes (mobile) | Each new screen | Each milestone |

### 5.2 Rules
- Tests are deterministic. No real network calls in unit or integration tests: vendors are faked behind their adapter interfaces. The fake for each adapter lives next to the interface.
- Time is injected (a `Clock` service). Tests never depend on the real date.
- Test data built with factories in `apps/api/test/factories/`, not hand-written SQL.
- Coverage target: 90% lines for `billing`, `identity` and `ai` credit logic; 80% for other modules' services. Coverage is a floor, not a goal; meaningful assertions matter more.
- A bug fix starts with a failing test that reproduces the bug.
- Never skip, delete or weaken a test to get green. A flaky test is fixed or quarantined with a linked task and a human's approval, within the same week.

## 6. Error handling

- Standard error response: `{ error: { code: "BOOKING_SLOT_TAKEN", message: "That time was just booked. Please pick another.", details?: {...}, requestId } }`.
- Error codes are a typed enum in `packages/contracts/errors.ts`. Clients switch on `code`, never on `message`.
- Expected failures (validation, not found, conflict, payment required, insufficient credits) are typed results, not thrown exceptions, inside services.
- Unexpected errors are thrown, caught by a global filter, logged with the request ID, reported to Sentry, and returned as `INTERNAL_ERROR` with no internal detail.
- Every external call has a timeout, a retry policy appropriate to whether it is idempotent, and a circuit breaker for vendors that can be degraded (AI, video, calls).
- UI shows a helpful message and a next step for every error code. Never a raw error.

## 7. Performance budgets

| Measure | Budget |
|---|---|
| Mobile cold start to interactive dashboard (mid-range Android, 4G) | under 2.5 s |
| API p95 latency, read endpoints | under 200 ms |
| API p95 latency, write endpoints (non-AI) | under 400 ms |
| AI chat time to first streamed token | under 2 s p95 |
| Web marketing pages Largest Contentful Paint | under 2.0 s |
| JS bundle (mobile) growth per release | flagged in CI if above 5% |
| Crash-free sessions | 99.5% or better |

Budgets are checked in CI where possible and in staging before each release.

## 8. Accessibility and UX quality

- WCAG 2.2 AA on web. Equivalent on mobile: screen reader labels, Dynamic Type or font scaling up to the largest accessibility sizes without layout breakage, 4.5:1 text contrast, 44 by 44 pt touch targets, Reduce Motion respected.
- Every screen designs its loading, empty, error and offline states.
- Dark mode supported from Phase 1 via tokens.
- Haptics used purposefully (completion, streak, booking confirmed).

## 9. Internationalisation

- No user-facing string is hard-coded. All text in `packages/i18n` catalogues with keys like `onboarding.goals.title`.
- Dates, times, numbers and money formatted through shared helpers using the user's locale and time zone.
- Layout must survive 40% longer text (German) and right-to-left (future).
- English (UK) is the source language at launch. (Open question: confirm launch market.)

## 10. Security practices

- Secrets: never committed. `gitleaks` in CI and as a pre-commit hook.
- Dependencies: Renovate bot for updates, grouped weekly. `pnpm audit` and GitHub Dependabot alerts. No dependency with a known high or critical vulnerability ships.
- Static analysis: CodeQL on the repo.
- Every new endpoint reviewed against the checklist: authenticated? permission? ownership? validated? rate limited? logged without sensitive content? idempotent if needed?
- Least privilege for every service key (separate keys per environment, scoped where the vendor allows).
- Security review before each phase launch (see `05-launch-readiness.md`).

## 11. Git workflow and CI

### 11.1 Branching
Trunk-based. `main` always releasable. Short-lived branches, merged by pull request with squash merge. No long-lived feature branches; unfinished work hides behind flags.

### 11.2 CI pipeline (GitHub Actions), on every PR

1. Install with pnpm cache.
2. `pnpm lint` (includes boundary rules).
3. `pnpm typecheck`.
4. `pnpm test` (unit).
5. `pnpm test:integration` (Testcontainers Postgres).
6. Migration check: apply all migrations to an empty database and to a copy of the previous release's schema; verify drizzle schema has no drift from migrations.
7. `pnpm contracts:check` (breaking-change check).
8. Build all apps.
9. Secret scan, dependency audit, CodeQL.
10. Web preview deploy plus Playwright smoke tests.
11. If files under `apps/api/src/modules/ai/prompts/` or AI config changed: `pnpm test:ai-evals` (requires label `run-ai-evals` to control cost).

A PR cannot merge with any red check. Required reviews: one human approval for anything touching `billing`, `identity`, `ai` safety, migrations, or infrastructure.

### 11.3 Release process
- **API and web:** merge to `main` deploys to staging automatically. Production is a manual promotion of the exact staging artefact, after smoke tests pass. Database migrations run as a separate release step before the new code goes live.
- **Mobile store builds:** EAS Build from a tagged commit. Internal testing (TestFlight and Play internal track) first, then staged rollout (Play) or phased release (App Store) over 7 days, watching crash-free rate and key metrics.
- **Mobile over-the-air updates (EAS Update):** allowed only for JavaScript and asset changes compatible with the current native runtime version. Never used to change purchase flows or anything that would breach store review rules. Rolled out to a percentage first, with automatic rollback if the crash rate rises.
- **Feature flags** control exposure. A feature goes: internal → beta testers → 10% → 50% → 100%. Flags are removed within two releases after reaching 100%.
- Every release has a changelog entry and can be rolled back: previous container image for API and web, previous OTA update for mobile, and every migration designed to be backward compatible with the previous code.

## 12. Documentation

- Every module folder has a short `README.md`: purpose, owned tables, published events, consumed events, public interface.
- Docs change in the same PR as the code.
- Runbooks in `infra/RUNBOOK.md` for: deploy, rollback, rotate a secret, restore the database, handle a payment incident, handle an AI cost spike, handle a safety incident, process a data deletion request.
